# Runbook: live test with Codex text and images, Jev and fal SAM

Written 2026-11-02 from a working session. It records the exact settings that got the game
running with text and image generation through the Codex CLI, decisions through Jev and
segmentation through fal, and every trap hit on the way. Secrets are never written here:
the Jev and fal keys come from the project `.env` and are passed to the game process only.

## What this test uses

| Concern | Provider | Switch |
|---|---|---|
| Storyteller and NPC text | Codex CLI (ChatGPT login, subscription) | `DF_GAMEPLAY_CODEX_MODE=on` |
| Typed-line and choice decisions | Jev (SystemOne) | `DF_JEV_API_KEY` |
| Character and scene images | Codex CLI image backend | `DF_IMAGERY_MODE=live`, `DF_IMAGERY_BACKEND=codex-cli` |
| Image segmentation (SAM) | fal | `DF_FAL_KEY` |
| Creator image classification | Jev | `DF_GAMEPLAY_CREATOR_JEV_API_KEY` |
| OpenAI API, voice, music, speech input, video | off | `DF_GAMEPLAY_DISABLE_OPENAI_API=on` and `*_=off` |

All text and image calls go through the durable text service and the image service. Nothing
here calls a provider directly.

## Status of each part

Proven end to end (run 49, 2026-11-02):

- Codex storyteller attempts run and are recorded in `df_text.text_attempt` (profile
  `storyteller-codex`); Jev choices settle in the same table (profile `systemone-jev`).
- A typed hero line is judged by Jev and the NPC answers through the Codex storyteller in the
  transcript (`dev say` returns `npc_outcome: spoken`).
- Heroes, courier, bandit and the room are generated by the Codex image backend, cut out by fal
  (extraction stage) and published: `ART ready ... source=live`, about 90 to 210 s each with
  three image workers.
- Scene plates are generated by Codex, published and shown: `PLATE projected ...
  state=PLATE_STATE_READY effective_source=live_plate`, and the display page shows the plate
  with the generated characters and the NPC line.

- The phone creator works: `http://127.0.0.1:63329/gameplay/player?room=<code>` (the code is on
  the `JOIN url=` log line). Pick a non-dwarf ancestry, press Generate portrait, and about 100 s
  later the figure shows in an arched niche. Tapping it opens a full-screen review with Reroll
  and Keep portrait. Check this by looking at the phone view, not only the log.

Known limits:

- The party mural is refused (`ART failed subject=place:party-mural status=invalid_request`).
  It is OpenAI-only by design; the neutral stand-in is used.
- Codex has no quality setting and cannot write transparency; the fal extraction stage does the
  cut-out.
- The Codex image tool picks its own picture size (for plates about 1672x941). The candidate
  keeps its real size and the local transform resizes it to the delivered profile.

## Prerequisites

1. A built server and web client. See "Build" below; the launcher's own build step is not
   usable here.
2. The dedicated Codex home `artifacts/tmp/codex-text-home`, signed in with ChatGPT and with
   **no** `config.toml`. Sign in with
   `CODEX_HOME=<that folder> codex login`. Never copy or read its `auth.json`.
3. A scratch folder for Codex text turns that is outside any git repository and any
   directory containing `AGENTS.md`, for example
   `C:\Users\mreca\AppData\Local\Temp\df-codex-work`.
4. A second folder for Codex image jobs under the same rules, for example
   `C:\Users\mreca\AppData\Local\Temp\df-codex-image-jobs`.
5. The Codex executable path, its SHA-256 and its version:
   `C:\Users\mreca\AppData\Local\Programs\OpenAI\Codex\bin\codex.exe`,
   `certutil -hashfile <exe> SHA256`, `<exe> --version`.
6. `DF_JEV_API_KEY` and `DF_FAL_KEY` present in the project `.env` (names only are needed
   here; values stay in the file).
7. PostgreSQL binaries at `artifacts/build/imagery-postgres-18.6/pgsql/bin`.
8. Free disk space. A full disk breaks the build silently and leaves an empty web client.

## Build

The launcher builds offline against `artifacts/cache/cargo`, which is gutted, so its build
fails ("no matching package named prost"). Build with the normal cargo cache and launch with
`--no-build`:

```bash
cd /c/Users/mreca/Desktop/dungeonfluxGame
A="$PWD/artifacts"
export PATH="$A/cache/cargo/bin:$PATH" CARGO_TARGET_DIR="$A/build/start-s00" RUST_MIN_STACK=67108864
unset CARGO_HOME RUSTUP_HOME
set -eo pipefail
cargo build --locked -j 3 -p df-tools --bin df-transport-fixture
cargo build --locked -j 3 -p df-tools --lib --target wasm32-unknown-unknown
S="$A/tmp/play-run-tmp/wb.$$"; rm -rf "$S"; mkdir -p "$S"
wasm-bindgen --target web --out-name df_tools --out-dir "$S" \
  "$CARGO_TARGET_DIR/wasm32-unknown-unknown/debug/df_tools.wasm"
test -s "$S/df_tools_bg.wasm" && test -s "$S/df_tools.js"
rm -rf "$CARGO_TARGET_DIR/play-web"; mv "$S" "$CARGO_TARGET_DIR/play-web"
```

Check `ls -l artifacts/build/start-s00/play-web`: `df_tools_bg.wasm` is about 30 MB. A zero
byte file means the disk filled. Delete stale per-lane cargo target folders under
`artifacts/build` (keep `start-s00` and the PostgreSQL folders) and rebuild.

## Launch

Run from a Git Bash shell. This starts the game in the background, provider-limited as in the
table above.

```bash
cd /c/Users/mreca/Desktop/dungeonfluxGame
A="$PWD/artifacts"
W=/c/Users/mreca/AppData/Local/Temp/df-codex-work
J=/c/Users/mreca/AppData/Local/Temp/df-codex-image-jobs
mkdir -p "$W" "$J"
EXE='C:\Users\mreca\AppData\Local\Programs\OpenAI\Codex\bin\codex.exe'
SHA=$(certutil -hashfile "$EXE" SHA256 | sed -n 2p | tr -d ' \r')
VER=$("$EXE" --version | tr -d '\r')

# Build and database layout
export DUNGEONFLUX_BUILD_ROOT="$A/build/start-s00"
export DUNGEONFLUX_POSTGRES_BIN="$A/build/imagery-postgres-18.6/pgsql/bin"
export DUNGEONFLUX_PLAY_ROOT="$A/tmp/play-run" DUNGEONFLUX_TMP_ROOT="$A/tmp/play-run-tmp"
export DF_IMAGERY_OBJECT_ROOT="$A/tmp/play-run/private-images"
export DF_GAMEPLAY_DATABASE_PORT=55527 DF_GAMEPLAY_LISTEN=127.0.0.1:63329

# Never load .env wholesale: that turns every provider on
export DF_GAMEPLAY_LOAD_DOTENV=off DF_GAMEPLAY_DEV_CONTROL=on DF_GAMEPLAY_DEV_OVERRIDES=off
export DF_GAMEPLAY_VOICE=off DF_GAMEPLAY_STT=off DF_GAMEPLAY_MUSIC=off
export DF_GAMEPLAY_HOME_VIDEO=off DF_GAMEPLAY_SCENE_VIDEO=off DF_GAMEPLAY_CHARACTER_VIDEO=off

# Codex storyteller
export DF_GAMEPLAY_STORYTELLER=on DF_GAMEPLAY_CODEX_MODE=on DF_GAMEPLAY_DISABLE_OPENAI_API=on
export DF_GAMEPLAY_CODEX_HOME="$(cygpath -w "$A/tmp/codex-text-home")"
export DF_GAMEPLAY_CODEX_WORKDIR="$(cygpath -w "$W")"
export DF_GAMEPLAY_CODEX_EXECUTABLE="$EXE" DF_GAMEPLAY_CODEX_SHA256="$SHA" DF_GAMEPLAY_CODEX_VERSION="$VER"

# Images through Codex
export DF_GAMEPLAY_IMAGERY=on DF_GAMEPLAY_PLATES=on DF_GAMEPLAY_CREATOR_PORTRAITS=on
export DF_IMAGERY_MODE=live DF_IMAGERY_BACKEND=codex-cli DF_IMAGERY_QUALITY_PROVIDER_QUALITY=none
export DF_IMAGERY_CODEX_EXECUTABLE="$EXE" DF_IMAGERY_CODEX_WORKDIR="$(cygpath -w "$J")"
export DF_IMAGERY_BACKEND_FAL_ENABLED=on DF_IMAGERY_DATABASE_CONNECTIONS=8
# A Codex image takes 90 to 260 s; the default 240 s job and 170 s stage limits expire first
export DF_IMAGERY_SCHEDULER_JOB_DEADLINE_SECS=900 DF_IMAGERY_SCHEDULER_STAGE_DEADLINE_SECS=600
export DF_IMAGERY_SCHEDULER_QUEUE_AGE_SECS=900

# Jev and fal SAM: only these two values are read from .env, and never printed
export DF_JEV_API_KEY="$(grep -m1 '^DF_JEV_API_KEY=' .env | cut -d= -f2- | tr -d '\r"')"
export DF_FAL_KEY="$(grep -m1 '^DF_FAL_KEY=' .env | cut -d= -f2- | tr -d '\r"')"
export DF_GAMEPLAY_CREATOR_JEV_API_KEY="$DF_JEV_API_KEY"

bash development/run-gameplay.sh --no-build --harbor --new-game > "$A/tmp/game-run.log" 2>&1 &
```

Wait for these lines in `artifacts/tmp/game-run.log`:

```
GATES storyteller=on memory=on voice=off ... pictures=on plates=on creator_portraits=on ... jev=on
STORYTELLER on model=codex-cli
APPROACH on model=jev-latest
IMAGERY on service=durable
DEV CONTROL on url=http://127.0.0.1:63329 token_file=...\dev-control-token
```

The display is `http://127.0.0.1:63329/gameplay/display`. The token file path is on the
`DEV CONTROL` line; export it for the dev CLI:

```bash
export DF_DEV_CONTROL_URL=http://127.0.0.1:63329
export DF_DEV_CONTROL_TOKEN_FILE='<path from the DEV CONTROL line>'
F=artifacts/build/start-s00/debug/df-transport-fixture.exe
```

## Play

`dev play --to dialogue` stops at character creation ("creation group draconic-ancestry has
no valid default"), so build the party by hand. Defaults give two Dwarf Fighters.

```bash
$F dev join 1; $F dev join 2
$F dev --timeout 240 create 1 Brakka
$F dev --timeout 240 create 2 Sigrun
$F dev --timeout 240 play --to dialogue
$F dev --timeout 240 say Brakka "Finn, who sealed that packet?" --context question
$F dev transcript
$F dev state
```

The scene's NPCs are Finn Alder (courier) and Dain Rusk. `dev say` needs a long timeout
because a Codex reply takes about 30 seconds and a follow-up content check about 15 more.

## Observe

```bash
$F dev gates                      # which capabilities are allowed this run
$F dev text config                # purposes, profiles, limits
$F dev text list                  # durable attempts, phases, usage
$F dev imagery                    # effective image config and runtime (running: true)
$F dev imagery events --last 40   # image job lifecycle; no refusal reason is shown here
```

Image refusals carry only a class in the events. Read the reason from the game database:

```bash
PSQL=artifacts/build/imagery-postgres-18.6/pgsql/bin/psql.exe
DB=<database named on the "Playing with database" line>
$PSQL -h 127.0.0.1 -p 55527 -U df_gameplay_demo_admin_20261004 -d $DB -Atc \
  "select reason, count(*) from imagery.image_no_delivery group by 1"
$PSQL -h 127.0.0.1 -p 55527 -U df_gameplay_demo_admin_20261004 -d $DB -Atc \
  "select dispatch_state, coalesce(failure_cause,''), local_accounting, count(*) \
   from imagery.image_dispatch_attempt group by 1,2,3"
```

A real Codex generation shows `image.sent` and then a long gap (about a minute or more)
before `image.completed`, and `codex.exe app-server` running from the configured path.
A job that completes in about one second with 1955472 output bytes is a local transform of
an existing picture, not Codex output.

## Stop and restart

```bash
$F dev shutdown        # exits 1 with "image reconfiguration fence unavailable"; seen on every stop
```

Wait about 12 seconds before relaunching so the owned PostgreSQL stops. Every launch with
`--new-game` makes a fresh database, so the heroes must be created again. To resume a game use
`--database <name>` instead of `--new-game`.

## Traps and fixes

1. **Disk full.** The build fails or writes an empty web client; the server then stops at
   `STARTUP step=assets outcome=failed`. Free space under `artifacts/build` first.
2. **The launcher cannot build.** Use the normal cargo cache (see Build) and `--no-build`.
3. **Providers turn on by themselves.** Without `DF_GAMEPLAY_LOAD_DOTENV=off` and explicit
   `off` gates the server reads `.env` and enables everything, including paid providers.
4. **Codex text mode refuses to start.** It needs all of: `DF_GAMEPLAY_DISABLE_OPENAI_API=on`,
   a dedicated home with no `config.toml`, an absolute scratch folder outside any repository
   (`safe non-repository scratch directory` otherwise), an absolute executable with matching
   SHA-256, and `DF_GAMEPLAY_CODEX_VERSION` equal to `codex --version` (the built-in default
   is 0.150.1; the installed CLI was 0.164.0).
5. **Typed lines are refused with "could not be judged".** Jev is off without
   `DF_JEV_API_KEY`. The log shows `LINE_JUDGEMENT ... reason=provider_unavailable`.
6. **Image runtime is `local-only` or off.** The default mode is `local-only`. Set
   `DF_IMAGERY_MODE=live`. `dev direct plate` answers "imagery is off" until then.
7. **A relative `codex` executable kills the image runtime.** The image backend requires
   absolute paths for `DF_IMAGERY_CODEX_EXECUTABLE` and `DF_IMAGERY_CODEX_WORKDIR`. A bad
   value makes the runtime worker fail (`image.failed worker`, `runtime_unavailable`) and a
   live `dev imagery set` cannot revive it. Fix the environment and restart.
8. **`DF_GAMEPLAY_CODEX_*` do not configure images.** The image service ignores them. Set the
   `DF_IMAGERY_CODEX_*` variables separately.
9. **Every job refused as `unsupported_profile`.** The Codex image backend rejects any
   quality setting, and the game gives each image purpose a `medium` or `high` override.
   `DF_IMAGERY_QUALITY_PROVIDER_QUALITY=none` makes the service clear them. Confirm with
   `$F dev imagery`: no purpose should have a `quality_override`.
10. **Creator portraits and hero images need an analysis route.** Without a Jev route for
    classification the creator flow has nothing to classify with. `DF_GAMEPLAY_CREATOR_JEV_API_KEY`
    adds it. OpenAI vision stays off, so inspection and head-location routes stay empty.
11. **NPC reply seems abandoned at about 45 seconds.** That was the dev client's own 60 s
    timeout, not the server. Use `--timeout 240` and read the reply from `dev transcript`.
12. **The dev client times out at 60 seconds.** Pass `--timeout 240`. The server keeps working
    after the client gives up; `dev state` shows whether a write committed.
13. **Rebuilds silently do nothing while the game runs.** The executable is locked by the
    running server (and by polling monitors that call it). Use
    `artifacts/tmp/rebuild-and-launch.sh <log>`: it shuts the server down, waits for the process
    to exit, builds with retries, checks the executable was replaced and relaunches.
14. **Plate or character jobs fail at 170 s or 240 s.** Codex images take 90 to 260 s. Raise
    `DF_IMAGERY_SCHEDULER_JOB_DEADLINE_SECS=900`, `..._STAGE_DEADLINE_SECS=600` and
    `..._QUEUE_AGE_SECS=900` (the launch script does). The HTTP clients cap every single
    request at 180 s regardless (`HTTP_TIMEOUT_CEILING`).
15. **Jev classification returned HTTP 400.** The SystemOne API rejects `max_output_tokens` at
    any value; the classification body must not carry it.
16. **Image runtime dies a few minutes in** (`IMAGERY runtime_stopped` or `runtime_worker_ended`
    in the game log). The worker loop only survives a list of errors; a stage that disagrees with
    its stored state (`OperationConflict`, `LostClaim`, `Superseded`) is now survivable and the
    stage is retried by recovery. Any other error still ends the runtime, so grep for these
    lines first when images stop.
17. **One image worker is too slow.** The supervisor starts `foreground_limit` (1 to 4) workers;
    Codex jobs run in parallel, so three workers cut the character wait from about 10 minutes
    to about 3.
18. **Plates stay on the old picture and the demand ends `deadline_exceeded` after 900 s.**
    Seen when the Codex picture size did not match the plate profile: the candidate check
    refused the picture without a log line and the stage stayed `sent` until recovery failed
    it. Fixed by checking Codex candidates at their real size. To see this class of problem,
    compare `dev imagery events` per job: a job that stops after `usage_projected` with no
    `candidate_checkpointed`/`output_stored` was refused.
19. **Debug builds are far too slow at hashing and image work.** SHA-256 and the image codecs
    ran at about 1 MB/s unoptimized, and the game re-hashes every reference image on each
    poll of a job, which starved the async workers. `Cargo.toml` now optimizes `sha2`, the
    image codec crates and `df-imagery` in the dev profile. If images stall with the process
    pinned at one core, take a stack dump
    (`cdb.exe -pv -p <pid> -y artifacts/build/start-s00/debug -c ".lines -e; ~*k 40; qd"`).
20. **`dev imagery events` and `dev imagery` are the first place to look** for stuck jobs; the
    database is reachable with `psql -h 127.0.0.1 -p 55527 -U df_gameplay_demo_admin_20261004
    -d <run database>` (see the `Playing with database:` line in the game log).
21. **Resuming a game across a rebuilt binary can mislead.** Jobs recorded by an older binary are
    recovered by the new one; judge a fix only on a fresh game (`--new-game`).

22. **Creator portrait finishes in the log but never shows on the phone.** The server answers
    with a signed address of about 345 characters
    (`/gameplay/creator-portrait/<64 hex>?g=<250 hex>`); the phone client used to drop any
    address over 128 characters. The limit is now 512. If it regresses, the log shows
    `CREATOR_PORTRAIT ... outcome=ready` and the stage keeps its placeholder.
23. **First portrait request says "The portrait result is unknown".** The first read after the
    job commit could return `Unknown` (the job moved between two reads); the creator treated that
    as final and the phone stopped polling while the job ran on. The request is now retried
    (`retry_unknown`) like the game's own image calls.
24. **The dev ticket page (`dev screen <seat>`) can fail with "development player scope
    invalid".** Use the real player URL above instead.
25. **Test environment.** `df-persistence` imagery suites need
    `DUNGEONFLUX_REQUIRE_SCRATCH_PG=1` and, for `imagery_service`, also
    `DUNGEONFLUX_RUNTIME_PG_PORT=55471`; `imagery_execution` uses 55471 by default. Run the
    `df-tools` imagery groups without the scratch flag. Parallel runs while the game is
    building time out on a cluster-wide lock; use `-- --test-threads=4` or fewer.

## After the test

Stop the game with `dev shutdown`. The scratch folders under `AppData\Local\Temp` and the
`artifacts/tmp/play-run*` folders can be deleted. Nothing here changes the repository. If the
run changes any of the settings above, update this file in the same change.
