# Atomic imagery publication

The publication boundary implements image-generation-architecture.md's durable-byte-before-Ready sequence and service-composition.md sections 6 and 7. It writes no finance state and starts no provider work.

`df_assets::ImageProof::decode` takes one written `VariantRecord`, its exact encoded bytes, the complete frozen recipe digest, and the expected `ImageIntent`, and typed injected `ImageProofLimits`. It checks length and SHA-256 against that record, refuses animation and unsupported formats, enforces the caller's encoded-byte, pixel and decoder-allocation budgets, decodes the image, and measures MIME, dimensions and actual alpha. `ImageIntent` validates positive database-representable dimensions without an upload-derived pixel cap. Default standalone limits are 64 MiB encoded bytes, 20 million pixels and 160 million decoder bytes; production uses the retained runtime configuration instead. The alpha scan reads native 8-bit or 16-bit pixel channels without allocating another image, so near-opaque 16-bit pixels remain transparent. `ImageAlphaRequirement::Preserve` accepts both opaque and transparent output; the proof and published result retain the actual observed alpha separately. Private fields prevent metadata-only construction. Run this CPU work on the runtime's bounded blocking worker before opening PostgreSQL transactions. The runtime must obtain bytes from the catalog's exact object key/version through the verified object-store read port.

`df_imagery::publication::FrozenOutput` is a revision-one canonical envelope containing separate master/display output requirements and bounded opaque canonical execution-recipe bytes. Composition retains the full selected inputs, config, model, profile and transform revisions in the execution recipe and derives the audience-aware media request key over the complete recipe. `snapshot()` is the payload to freeze and allocate. `recipe_digest()` hashes its revision and complete bytes with a domain separator. Unsupported legacy snapshots are refused during publication. This codec does not reinterpret consumer text or invent route decisions.

`finalize_image_in(tx, command)` requires READ COMMITTED. Its command names the owner, job, allocated output stage, current dispatch, execution claim/generation, held catalog attempt, finalization request, decoded proofs and injected time. The function locks quota then asset, followed by the exact job/stage/dispatch/cursor. It compares catalog ownership and request key, planned asset/attempt/output stage, immutable allocation and recipe/config snapshots, current dispatch, the exact immutable output checkpoint and every required winning variant/proof. Winner lookups are bounded to the one or two selected writes. It refuses stale execution and catalog claims before changing state.

Only then does it call the existing catalog finalizer and write immutable `image_job_result` and `image_result_variant` rows plus a single job revision increment in that transaction. Exact replay compares the retained full binding, winner order, manifests, object keys/versions and properties and returns `Existing` without another revision increment. A conflicting replay fails. Retired paid jobs with a succeeded current dispatch retain exact claim token/generation checks but may reconcile after the execution lease expires; the catalog publication lease must remain live. They may publish with the catalog origin account's private audience, while the job remains retired and no interest is recreated. Pure CPU retired work is refused; RecordOnly supplier work additionally requires exact known usable raw supplier output or the actual selected Candidate receipt. Absence of an origin account refuses private reconciliation. Private-only Ready cannot prove customer-delivered economic image use.

On an error, a caller using the transaction-taking API must roll back. `PostgresImagePublication::publish` owns the transaction and drops it on any precommit error. `commit_publication` maps only a failed commit acknowledgement to `Unknown`; recovery reconnects and calls the same owner/job result read before any retry. It must not regenerate or release financial uncertainty.

`PostgresImagePublication::open_existing` uses the established bounded pool with the composition's positive connection count and shared PostgreSQL transport policy; it never migrates. It implements neutral `ImageResults::read_result`. Result reads are owner-scoped and Ready-only, with an asset share lock preventing a concurrent lifecycle transition during the read. Cache reads additionally require exact recipe digest and audience, a live attached interest and a frozen live job, and exclude private reconciliations. Missing results remain `None`.

`resolve_publication_in` takes an owner and exact catalog asset/attempt (including those from a settlement outbox entry). It first requires the immutable allocation, follows its exact stage/current cursor through execution resolution, and reads that dispatch's output checkpoint in hosted or local mode. Unknown pairs are `NotFound`; later inspection touches cannot reroute them. The returned dispatch retains its own finance tuple; the catalog publication attempt is never interpreted as a finance attempt. Finance settlement and refund decisions remain finance-owned.

A separate `RecoveryLease` may authorize publication of a current succeeded dispatch after its normal stage lease expires. The atomic transaction validates that exclusive recovery token/generation through the execution journal while retaining the original dispatch claim lineage. A completed recovery acknowledgement reads the actual owner/job/stage/dispatch result receipt joined to a Ready catalog asset; the caller cannot attest success without it.

`NativeImagePublisher` implements the native `ImagePublisher` port over `PostgresMediaCatalog`, `PostgresImagePublication`, the configured `ObjectStore`, fresh runtime IDs and an injected clock. `PreparedImageOutput` supplies the exact master and optional display bytes; the adapter refuses missing or extra required variants and invents no derivative transformation. Bounded blocking workers validate staging bytes and revalidate exact version-pinned winning bytes before proof emission. Staging, catalog lease/variant records and output checkpoint survive restart; publication reads them again without an in-memory result map. `store_output` returns the final winning master checkpoint with the exact usage revision, then the worker records dispatch completion before `publish` finalizes Ready and its result. The local `ImageDispatchAdmission` implementation requires retained RecordOnly configuration and durable local stage accounting, uses the existing catalog admission and common allocation table, and has no hosted fallback. Hosted admission remains a distinct finance-owned composition.

Migration 0042 follows media 0010 and imagery 0038, 0039 and 0040; 0041 is independent. Draft funding's 0043 writes the same allocation table. The migration creates a dedicated NOLOGIN `df_imagery_publication` role, with only publication/catalog/quota/result privileges and timestamp-only execution lock privileges. It has no finance membership or table privileges. The separate `df_imagery_output` role inherits publication capability and adds only catalog staging/variant/admission capabilities. It cannot INSERT allocations directly or alter durable stage accounting mode. Its SECURITY DEFINER `allocate_local_output` entry point validates the exact durable Local stage, planned owner/job/stage/asset/attempt, frozen recipe/config, catalog ownership and active demand; the nullable ownership predicate requires `IS TRUE`. Hosted stages are refused. Deployment configures its login independently and must preserve the least-privilege role. No PUBLIC grants are added.

The PostgreSQL test suite requires `DUNGEONFLUX_REQUIRE_SCRATCH_PG=1` and the existing owned loopback PostgreSQL on port 55471. It creates and drops uniquely named scratch databases, persists actual encoded PNGs through `NativeFileStore`, reopens the store, and decodes version-pinned bytes before publication. There are no live provider calls. Independent integration and running-output review remain required before enabling hosted dispatch.

## Resumed pipeline and source boundary, 2026-10-29

The original allocation anchor, request key, plan and config remain immutable. A separate final selection binds the actual LocalTransform dispatch and resolved execution recipe to that anchor, the actual measured Candidate, every candidate ancestor and exact decision references. Final stage config revision is the anchor's operator revision, distinct from config snapshot codec revision. Intermediate paid image stages retain Candidate receipts and their own finance identities; a Hosted job's final CPU stage remains Local with no supplier tuple. A pipeline requiring final selection cannot use the legacy direct-output publication path.

Native qualification loads actual retained decisions and raw usage in a short read transaction and replays their frozen semantic policy on bounded CPU work outside publication locks. Atomic selection and Ready compare the protected qualified proof with exact current metadata and the complete actual ancestor graph. Missing Required inspection, rejected candidates and uncertain/revise classification refuse; explicit BestEffort Unjudged preserves its actual failure and Unknown liability.

Every canonical external source has a durable ordered SourceReceipt, including an explicit empty snapshot. The receipt pins asset/digest/audience, attempt, winning write/version, suppression generation and retention class. Final publication locks current grant authority, then output quota, sorted source/output asset rows, then job/stage/cursor, and revalidates all pins. A host-owned object-safe transaction callback rechecks current grants and retention lifecycle; source-bearing publication fails closed without it. Native Local Sent holds those source/grant locks while calling the execution owner's narrow Sent gate in the same transaction. Only New authorizes transport; AlreadySent preserves uncertainty without another send.

The output role's narrow Local outcome helper mirrors settlement only for exact durable Local/no-finance state. It cannot settle Hosted supplier liability. Replay is read-only and Unknown remains outstanding. Canonical finance reads actual Ready contribution through `stage_economic_use_in` under its existing job lock, without adding catalog/execution locks. Selected Candidate, superseded Candidate, private-only undelivered Candidate and useful Decision are separate typed evidence with exact usage revision. Raw decision validity and all Unknown billing remain finance-authoritative; absence is no negative proof.
