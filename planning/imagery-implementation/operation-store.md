## Identity and immutable data

Reuse ImageOwner, OperationIdentity, df_types::OperationId and df_assets::MediaRequestKey. Add distinct16-byte ImageJobId and ImageInterestId value types only; use existing ID conventions. Operation fingerprint binds immutable canonical consumer intent, NOT later supplier/classification decisions; caller-created fingerprint is checked by the future service. Store compares fingerprints and the complete immutable intent snapshot on replay, never just a hash collision assumption.

VersionedSnapshot stores nonzero format revision plus exact opaque canonical bytes, with redacting Debug. Store does not claim to parse or authorize that payload. Its constructor takes injected snapshot byte limit and rejects overflow/empty/oversize; actual bytes are durably retained, not merely configuration revision. Separate intent and config snapshots. Configuration differences do not turn replay of an existing operation into a new job: operation replay returns the original frozen job/config. New operations may join only when owner, sharing-policy identity, intent snapshot and config snapshot match exactly. Operation ID is excluded from intent snapshot so compatible distinct operations can join.

Sharing-policy identity is a32-byte opaque digest produced by the future service over source/audience/lifetime/execution compatibility; it is not MediaRequestKey. No automatic sharing based merely on equal image bytes. Store checks full supplied intent/config equality alongside it; service remains responsible for semantic authorization. Fresh regeneration must use different intent/freshness identity and cannot join old work.

Absolute Unix-millisecond deadline is i64 checked positive and greater than accept time for NEW demand. All now/deadline values are injected. Replay returns existing outcome even after expiration; no automatic new work. Join preserves and reports existing job deadline, never extends it, and refuses expired/retired jobs. IDs, timestamps and limits are injected; no environment reads, UUID entropy, wall clock or provider effects in neutral types.

## Records and schema

Three new PostgreSQL tables in imagery schema, with length/nonzero/revision/state/FK checks and no PUBLIC grants:
- image_job: job_id PK; owner_scope canonical bytes; sharing_identity32; exact versioned intent/config snapshots; absolute_deadline_ms; state Planning/RecipeFrozen/Retired; revision positive bigint; resolved_recipe_key nullable32; frozen_recipe revision+bytes nullable; created_at_ms/updated_at_ms. Planning has no resolved key/recipe. RecipeFrozen has both. Retired preserves any previous key/recipe; no Ready/publication/finance state. Snapshot pairs must be internally consistent. Store canonical owner bytes from typed ImageOwner with explicit version/tag and exact campaign/run or account IDs; no Debug/text-derived keys.
- image_operation: (owner_scope, operation_id) composite PK; fingerprint32; job_id FK; interest_id FK unique; immutable receipt. Many operations may reference one job. Different owner scopes may use identical operation bytes.
- image_interest: interest_id PK; owner_scope; job_id FK; operation_id binding; Attached/Withdrawn; created_at_ms; withdrawn_at_ms consistency. A withdrawn interest remains recorded; replay must not revive it. Composite owner/job references/checks prevent inconsistent linkage.
No table stores money, supplier requests, credentials, raw URLs or successful asset publication. Payloads may include private intent/config facts and must never appear in errors/Debug/logs. No fake ability to dispatch from Planning/RecipeFrozen.

## Exact operation semantics

ImageJournal trait methods return named typed commands/results/errors and Send futures following existing port style:
1. accept(command): atomic receipt lookup/create-or-explicit-join + interest. Command contains OperationIdentity, immutable intent/config snapshots, sharing identity, supplied new interest ID, and target Create { new_job_id, deadline_ms } or Join { existing_job_id }, plus now_ms. Existing scoped operation with same fingerprint AND intent returns Replay(original receipt, current job, current interest) without modifying anything; changed intent/fingerprint -> OperationConflict. For a new operation, Create creates one Planning job plus receipt+Attached interest in one transaction. Join row-locks existing exact-owner job, checks current state/deadline/sharing+intent+config equality, then creates receipt+interest in one transaction and increments job revision. Same-operation races cannot leave orphan jobs/interests. Supplied ID collision never overwrites data. No fallback from refused Join to Create.
2. lookup_operation(owner, operation): typed optional receipt + current job/interest read as one coherent snapshot (prefer one joined SQL statement; multiple READ COMMITTED queries alone do not guarantee consistency). Wrong owner cannot reveal another scope's receipt/job.
3. read_job(owner, job): typed optional job. Reads return retained frozen snapshots, actual revision/deadline and no invented result.
4. freeze_recipe(command): owner+job+expected_revision+resolved MediaRequestKey+exact versioned recipe snapshot+now_ms. Planning at expected revision becomes RecipeFrozen with key/snapshot atomically, increments revision. Replay precedence: an existing identical frozen key AND recipe returns AlreadyFrozen even after retirement/expiry, without reviving work; an existing different frozen key/recipe returns RecipeConflict. Only first freeze checks retired/expired refusal, then expected revision (Stale { current_revision } if Planning revision differs); no network or classification occurs. Classification decisions must be inside or durably referenced by the future service's freeze payload; this slice does not claim it executes or stores independent paid stages.
5. withdraw_interest(owner, interest, now_ms): atomic owner/job/interest checks, Attached->Withdrawn and job revision increment. Return Withdrawn or AlreadyWithdrawn plus current remaining attached count/revision. With other interests, preserve Planning/RecipeFrozen. Last withdrawal sets Retired while preserving frozen facts. Never delete receipts or create replacement work. Repeated withdrawal is idempotent and cannot revive anything.

Use typed failures: Unavailable (before known commit), Unknown (commit may have occurred), InvalidRecord, OperationConflict, IdentityConflict, JoinRefused(reason), NotFound, RecipeConflict, Stale, Retired/Expired as appropriate. Do not collapse Unknown into safe retry/new creation. All mutating commands are idempotently rereadable using supplied identities. Public enums expose only genuine possible outcomes, no hypothetical placeholders.

## Transaction/concurrency implementation

Use existing PostgreSQL transport and bounded owned connection lifecycle; reuse media_pool where appropriate without changing its unrelated behavior. Expose transaction-taking private statements so later catalog/finance composition can share a transaction. Public adapter owns one transaction per call. READ COMMITTED, parameterized SQL, bounded statement/lock/connection timeouts. Preserve source-error categories without leaking payloads.

Serialize scoped operation acceptance consistently (a deterministic transaction advisory lock over canonical owner+operation is acceptable; collisions only reduce concurrency). Then lookup receipt before creating anything. Join/freeze/withdraw lock job before interest; never lock two jobs in opposite order. Receipt uniqueness and FKs remain final DB constraints. Recheck all equality/state conditions under the lock. No transaction held over external work. Commit failure yields Unknown. New writes never erase old snapshots/receipts. Exact private helper names/schema index names are implementation choices.

Schema/migration opening must use the existing migration ownership pattern and no automatic destructive resets. Runtime service roles must get no new unconstrained table access; hosted authorization/definer binding is a later integration prerequisite. Actual tests use owned scratch databases and assert PUBLIC cannot read/write these private rows. Do not present superuser tests as proof of complete hosted role integration.
